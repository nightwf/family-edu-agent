# 禾芽家庭 AI 私教技术架构方案（V2 提案）

> 状态：已评审通过，实施中
> 关联文档：`家庭AI私教产品方向需求文档.md`
> 关联技术设计：`TECHNICAL_DESIGN_V2.md`
> 更新日期：2026-09-05

## 0. 评审目标

本文档只回答一个问题：

> 如果要按照“先懂孩子，再定策略，再指导家长，并形成可验证改善周期”的方向重做，技术架构应该怎么调整？

本文档不包含具体代码、完整数据库字段或部署命令。

## 1. 现有架构与新产品方向不匹配的地方

现有系统已经有可用的 Web、小程序、Fastify API、PostgreSQL、MCP 和 WorkBuddy 开放平台包，但技术结构仍然是“数据功能后台”，不是“家庭教育决策系统”。

主要断点如下：

### 1.1 没有“目标与周计划”这一层

现有数据模型只有：

- `Record`：零散成长记录；
- `Report`：报告；
- `Homework`：学校作业；
- `RemediationPlan`：错题教学规划。

缺少一个统一承载“4–8 周主目标、每周计划、干预动作、复测、家长确认”的核心模型。

`RemediationPlan` 现在只围绕错题，无法承担统一周计划。

### 1.2 学生状态和证据没有真正建模

当前成长记录主要依赖自由文本和 `metadata`，无法稳定回答：

- 这条记录是在什么场景下发生的；
- 是事实、推断还是家长主观判断；
- 证据强度如何；
- 有没有相反证据；
- 后续有没有复测验证。

这会让“孩子状态”仍然只能展示，不能参与可靠的策略匹配。

### 1.3 教育方法仍然像配置项

现有 `education-methods.ts` 主要通过“兴趣优先、宽松、鼓励为主”等字符串匹配推荐方法。

这与已经确认的产品方向不一致：

- 家长应该设置边界，而不是选择教育流派；
- 方法应该有证据强度、适用条件和版本；
- 家庭个性化应该来自方法效果记录，而不是家长直接改全局方法。

### 1.4 AI 能力和项目能力没有清晰分层

当前 MCP 主要是 WorkBuddy 反向调用禾芽，缺少从禾芽到 WorkBuddy 的“规划任务请求”。

因此“AI 主动生成候选目标、主动生成每周计划”目前没有稳定的执行通道。

### 1.5 缺少后台任务

每周回顾、延迟复测、4–8 周阶段报告、计划到期提醒，都需要定时任务或异步任务，但当前只有一次 HTTP 请求内同步处理。

## 2. 目标架构总览

第一阶段不建议拆成微服务。建议保持“单 API 服务 + 独立 Worker”的部署形态，但把业务边界在代码层明确拆开。

```text
Web 家长管理端 / 微信小程序
        │ 登录态 JWT
        ▼
┌───────────────────────────────────────────────┐
│ Family Education API                          │
│                                               │
│  身份与家庭边界                                │
│  孩子上下文与当前状态                          │
│  证据与评估                                    │
│  目标与周计划编排                              │
│  教育方法与个性化                              │
│  教材/题库/错题/知识库等资源                   │
│  报告与家长指导                                │
└───────────────────────────────────────────────┘
        │                          ▲
        │ 计划上下文 / 结构化证据    │ MCP / Open API
        ▼                          │
┌───────────────────────────────────────────────┐
│ WorkBuddy Agent Gateway                        │
│ 负责大模型理解、讲解、生成题目、生成目标草案    │
│                                               │
│ 入站：WorkBuddy -> 禾芽 MCP                    │
│ 出站：禾芽 -> WorkBuddy 云端任务（后置）       │
└───────────────────────────────────────────────┘

数据层：
PostgreSQL          权威结构化数据
对象存储            教材、题目附件、原始文件
pgvector（可选）    知识检索
后台 Worker         周回顾、延迟复测、阶段报告
```

## 3. 分层职责

### 3.1 客户端层

Web 管理端和小程序只负责：

- 查看孩子当前状态；
- 查看本周计划；
- 确认、拒绝或微调 AI 提案；
- 查看证据和复盘；
- 维护家庭边界；
- 查看报告。

它们不承担 AI 生成、教学分析和题目生成。

WorkBuddy 负责：

- 对话和教学；
- 题目识别和讲解；
- 读取禾芽上下文；
- 生成目标草案、周计划、题目和练习；
- 把结构化证据写回禾芽。

### 3.2 API 领域层

建议按以下业务模块重组，而不是继续按“一张表一个路由”堆叠：

1. 身份与家庭：账号、家庭成员、邀请码、微信绑定、Token、会话。
2. 孩子上下文：孩子基础档案、家庭边界、当前阶段重点。
3. 证据与评估：行为观察、作业、答题、错题、练习、复测、证据来源。
4. 目标与计划：4–8 周目标、候选目标、周计划、任务、干预、确认和撤销记录。
5. 教育方法：公共方法库版本、证据强度、适用条件、家庭边界、方法效果记录。
6. 资源域：教材、知识库、题型、题目、错题、练习试卷。
7. 报告与家长指导：每周回顾、阶段报告、家长建议、复盘结果。
8. MCP 边界：把以上领域能力映射成 WorkBuddy 可调用的工具。

### 3.3 WorkBuddy Agent Gateway

项目不自己保存一套模型调用逻辑，而是把“禾芽需要 AI 做的事”统一描述成计划上下文，交给 WorkBuddy。

第一阶段建议使用两条通道：

- 同步通道：现有 Family Education MCP，由 WorkBuddy 调用；
- 异步通道：后续 WorkBuddy 开放平台云端任务，由禾芽发起请求，WorkBuddy 完成后回写。

产品方向已经确认：第一阶段先完成计划闭环，再接主动规划。因此异步通道只是架构预留，不要求当前立即实现。

## 4. AI 规划能力放在哪里

这是最容易出错的一层，建议坚持一个原则：

> 禾芽不重复建设第二套大模型能力，AI 生成仍由 WorkBuddy 完成；禾芽负责提供确定性的上下文、边界、证据和校验。

### 4.1 MVP 推荐流程

1. 家长在 Web 或小程序确认一个阶段目标；
2. 禾芽根据孩子状态、家庭边界和方法库，生成结构化 `PlanningContext`；
3. WorkBuddy 读取该上下文，生成 2–3 个候选目标或本周计划；
4. WorkBuddy 通过 MCP 写回候选方案；
5. 家长在 Web 中确认、修改或拒绝；
6. 禾芽把确认后的方案拆成任务，并在周期结束后生成复测证据。

这个流程不要求禾芽后端直接调用大模型。

### 4.2 后续主动规划

当 WorkBuddy 云端任务能力可用后，可以在不改变业务架构的情况下，把第 3 步变成异步任务：

> 禾芽创建计划生成任务 → WorkBuddy 云端执行 → 回写结果 → Web 通知家长。

这是 Agent Gateway 的扩展，不是新增一个独立 AI 服务。

## 5. 数据架构

### 5.1 PostgreSQL 是唯一业务事实来源

学生状态、家庭边界、目标、周计划、任务、方法效果、复测结果等，必须进入 PostgreSQL。

`JSONB` 只用于：

- 嵌套的教育方法定义；
- 题目选项和评分标准；
- 复杂证据明细；
- 外部系统返回结果。

不能把“今天读了多少、作业做没做、掌握度多少”继续作为自由 JSON 文件保存。

### 5.2 对象存储

教材、题目图片、上传附件等原始文件进入对象存储，PostgreSQL 保存文件标识、来源、版本和元数据。

### 5.3 知识库存储

知识库拆成三种内容：

- 原始资料：对象存储；
- 结构化事实：PostgreSQL；
- 可检索片段：PostgreSQL 全文检索起步，需要语义检索时再引入 `pgvector`。

第一阶段不建议一上来就加独立向量数据库。先用结构化字段和明确引用解决真实问题，等“按语义找相关教育经验”成为高频需求后再加。

### 5.4 证据不可覆盖

所有重要判断、状态变化、家长修正、AI 建议都应采用追加记录，不直接覆盖历史。

可以修改当前状态，但不能删除“曾经得出过什么结论、基于什么证据”。

### 5.5 知识、方法与计划都需要时间和版本语义

教材、知识点、教育方法、家庭边界和计划都有“随时间变化”的属性。不能只靠一个 `updatedAt` 判断有效性。

核心规则：

- 每条可替代内容都有 `status`：`active`、`archived`、`superseded`；
- 有 `validFrom` 和 `validUntil`；
- 被新版本替代时，旧版本标记为 `superseded`，并记录替代它的新版本；
- 默认检索只返回当前有效版本；
- 历史版本保留，但只在来源追溯、版本对比和家长主动查询时返回。

例如教材从 2024 版更新到 2025 版时：

- 新版本标记为 `active`；
- 旧版本标记为 `superseded`；
- 旧版的知识点、章节和引用继续存在；
- 新的学习计划默认使用新版；
- 已经生成的旧计划继续引用旧版，不改写；
- 家长要查看“这个结论来自哪一版教材”时，可以追溯到旧版。

### 5.6 孩子状态由时间窗口计算

孩子状态不应永久写死，也不应每次从全部历史重新计算。建议区分三种时间窗口：

- 最近 7 天：判断当前任务和日常状态；
- 4–8 周：判断当前改善目标是否有效；
- 6–12 个月：判断长期成长趋势。

孩子当前状态是一个“根据最近证据计算出的投影”，不是一条永远不变的记录。历史证据只参与趋势和解释，不直接当作当前事实。

一条过去的行为观察，如果没有最近的新证据，不能自动继续成立。系统应保留：

- 最初观察时间；
- 最近一次确认时间；
- 最新支持证据；
- 是否有相反证据；
- 当前置信度。

这样 WorkBuddy 拿到的就是“现在最可能成立的状态”，而不是“曾经发生过但可能已经过时的结论”。

### 5.7 年级变化需要触发重新评估

孩子从三年级升到四年级时，不是简单把年龄加一，而是要：

- 旧年级的学习目标和当前知识范围进入历史；
- 重新生成新年级对应的知识点和前置关系；
- 保留历史掌握证据，但不直接把“三年级已掌握”等同于“四年级仍掌握”；
- 对延续性知识点保留基础证据，对新知识点重新开始评估；
- 家庭边界和目标进入下一轮确认。

### 5.8 WorkBuddy 调用上下文包

为了避免把历史数据全部交给 WorkBuddy，每次调用应生成一个受控的“上下文包”，而不是全量查询。

上下文包默认包含：

- 当前孩子基础信息；
- 当前 4–8 周目标；
- 当前有效知识节点；
- 当前掌握状态；
- 最近 7 天相关证据；
- 当前适用的教育策略；
- 家庭时间预算和边界；
- 每个结论的来源与版本。

默认不返回：

- 其他孩子的数据；
- 已过期或已替代的知识；
- 长期历史记录；
- 与当前目标无关的教材、题目和报告；
- 未经确认的高不确定推断。

只有在家长主动要求对比历史、追溯来源或查看长期变化时，才扩展上下文。

上下文包中的所有判断和知识都应附带来源引用和版本，使 WorkBuddy 的回答可以被家长和系统校验。

检索顺序建议先走结构化条件，再考虑语义检索。结构化条件包括家庭、孩子、学科、年级、知识点、题型、状态、时间范围。未来引入向量库时，也不能绕过这些条件。

## 6. 建议的核心数据对象

以下不是最终表结构，而是为了说明领域边界。

### 6.1 家庭与账号

- 家庭；
- 用户；
- 家庭成员；
- 家庭邀请；
- 家庭级 MCP Token；
- 登录会话。

### 6.2 孩子与家庭边界

- 孩子基础档案；
- 家庭边界与偏好；
- 当前关注重点；
- 当前阶段目标。

### 6.3 学生状态与证据

- 证据记录；
- 行为观察；
- 作业与任务完成情况；
- 答题与错题证据；
- 复测记录；
- 状态判断和置信度；
- 待验证问题。

### 6.4 教育方法

- 公共方法版本；
- 方法定义与证据强度；
- 适用条件和风险；
- 家庭边界；
- 方法在具体孩子身上的效果记录。

### 6.5 目标与计划

- 4–8 周主目标；
- 候选目标；
- 周计划；
- 计划任务；
- 干预动作；
- 复测安排；
- 确认与撤销记录。

### 6.6 报告与家长指导

- 每周回顾草稿；
- 阶段报告；
- 家长建议；
- 建议执行结果；
- 复盘记录。

### 6.7 资源域

保留现有题库、错题本、作业、教材等能力，但重新归类：

- 家庭共享资源：教材、知识库、题目、题型；
- 孩子专属证据：作答、错题、掌握度、作业任务；
- 周期执行产物：周计划、复测、练习试卷。

## 7. 后台任务

建议增加一个轻量 Worker，处理：

- 每周回顾草稿生成；
- 到期复测提醒；
- 4–8 周阶段报告生成；
- 计划到期检查；
- 未来 WorkBuddy 云端任务轮询。

第一阶段可以用数据库任务表加定时扫描，不一定立即引入 Redis 和 BullMQ。规模上来后再升级，不影响领域设计。

## 8. 安全与权限

- Web 和小程序使用登录态身份；
- WorkBuddy 使用家庭级 MCP Token；
- 所有资源读写前必须校验家庭归属；
- 家庭成员按角色控制操作范围；
- 孩子相关数据遵守未成年人数据保护；
- 关键状态修改保留操作者、原因和前后值；
- 删除采用停用或归档，不直接销毁有证据关联的数据。

## 9. 部署形态

现有部署可以保留：

- 一台已有服务器；
- Nginx 使用 `/family-edu/` 路径；
- Docker Compose 运行 API、PostgreSQL、对象存储；
- 新增一个 Worker 容器；
- WorkBuddy 通过同一个远程 MCP 访问。

不新增第二个 MCP，也不改变其他系统的部署边界。

## 10. 数据迁移原则

账号、家庭和孩子档案必须保留。旧的教育过程数据可以先作为“只读历史证据”归档，不参与新的目标与计划计算。

新的目标、周计划、学生状态和方法效果从新模型开始积累，避免继续把自由文本当作核心业务数据。

## 11. 需要评审确认的架构决策

### 决策 1：单服务还是微服务

建议第一阶段继续单 API 服务加独立 Worker，不拆微服务。

### 决策 2：禾芽是否直接接大模型

建议不接。AI 生成由 WorkBuddy 完成，禾芽负责上下文、边界、证据和校验。

### 决策 3：知识检索是否立即引入向量数据库

建议先不引入独立向量数据库，PostgreSQL 结构化查询起步，确有需求后再加 `pgvector`。

### 决策 4：主动规划是否立即实现

建议先实现“计划 → 执行 → 复测 → 家长确认”闭环，WorkBuddy 云端任务后置。

### 决策 5：旧数据如何处理

建议保留账号、家庭和孩子，旧教育记录只读归档，不强行迁移进新模型。
